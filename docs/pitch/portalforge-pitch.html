PortalForge is open-source middleware for teams building on Portaldot V3. One product line: deploy and register contracts, index the chain, run workflows that survive failures, and verify the results on-chain.

The problem: Portaldot apps live on two interfaces at once

Two views of one event

Solidity runs inside pallet-revive. Every event is an EVM log and a native Revive event. EVM tools miss dispatch errors and runtime versions; Substrate tools miss ABIs.

Fragile automation

Teams glue scripts, cron jobs and webhooks. A lost response or a crashed worker means a job runs twice — or never — and nobody can prove which.

Unclear costs and state

Storage deposits hide inside “gas”, 14-dp tPOT shows as 18 dp, and there is no event filter API. Deployments are hard to plan and to verify later.

Measured on the live V3 testnet, not assumed. The EVM endpoint is the pallet-revive eth-rpc proxy; eth_newFilter is unsupported; a 2 KB contract holds about 160 tPOT of storage deposit.

Interfaces

Web console
TypeScript SDK · pf CLI
Idempotent receivers (demo service)

Shared state: SQLite (WAL)

Every multi-step write is one BEGIN IMMEDIATE transaction: cursor + events together; leases and state changes guarded by owner and expiry.

Least privilege

The API holds no chain key. The worker’s executor only calls allowlisted, nonpayable functions within a fee and rate budget.

Single-host design today: one database file, many processes. A hosted, multi-tenant version would move the store to PostgreSQL; the store interface was kept narrow for that.

Guarantee stated honestly: no duplicate business effect when the receiver deduplicates by executionId. Not exactly-once against arbitrary services.

All five rows are automated: the first three in the multi-process E2E with real processes, the last two on a real local chain. The demo video shows the first two live.

Advantages and a business hypothesis

Why teams would pick it

  • Portaldot-specific: dual interface, deposits, mapping, finality
  • Recovery semantics that are tested, not promised
  • Evidence anyone can re-verify with the CLI
  • Open source, self-hostable, one database file

Hypothesis (not validated)

  • Free: open-source core, self-hosted
  • Paid: hosted indexing with long history
  • Paid: team workspaces, SSO, alert channels
  • Paid: RPC/node observability for operators

No customers or revenue yet. Next step: interviews with Hacker House teams building on V3.

Be explicit that the business model is a hypothesis. The near-term value is for the ecosystem: it fills the middleware gap that every V3 app team currently rebuilds.
